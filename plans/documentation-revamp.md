# Documentation revamp implementation plan

## Problem statement

The current documentation proves behavior to maintainers, but it does not teach
the library to clients. It over-indexes on contracts, provenance, and test
evidence, while under-delivering on the actual user questions:

- What object hierarchy do I create?
- What code do I write?
- What does it look like on screen?
- Which widget should I use for a specific UI problem?
- How do menu/status commands, dialogs, focus, layout, themes, graphics, and
  platform services fit together in one application?

The Hello page is the clearest failure case: it describes behavior and tests,
but does not show the full source, object tree, screenshot sequence, or a
construction walkthrough. That is not credible client documentation.

## Target outcome

The documentation must convince a C++ client that ckVision is usable by showing
real code, real screenshots, and the object hierarchy behind every example.
After this work, a new user should be able to build a small app, choose layout
containers and widgets, wire commands/dialogs, and understand the rendering and
event model without reading the test suite or reverse-engineering headers.

## Documentation architecture

Create a client-facing documentation set under `docs/` with generated HTML/PDF
outputs under `docs/generated/`:

| Page | Purpose |
|---|---|
| `docs/getting-started.md` | Install/build prerequisites, CMake target, first application, run loop ownership, terminal expectations |
| `docs/tutorial-hello.md` | Full Hello walkthrough: source code, object tree, command registry, menu/status, message box, screenshots |
| `docs/object-model.md` | Application → root View → Desktop → docked chrome/windows/popups → widgets; ownership, focus, modality |
| `docs/layout-guide.md` | Row, Column, Grid, Dock, AnchorPane, Overlay, Splitter, frame overlays, resize/degradation examples |
| `docs/widget-gallery.md` | One section per widget/component with code snippet, screenshot, keyboard/mouse behavior, common mistakes |
| `docs/dialogs-and-commands.md` | Message boxes, descriptor dialogs, file/directory/window/help dialogs, command presentation, contexts |
| `docs/themes-and-rendering.md` | Roles, built-in schemes, per-subtree overrides, damage/presenter model at client level |
| `docs/graphics.md` | ImageView, Canvas, Sixel/no-graphics fallback, cell/pixel mouse, terminal profiles |
| `docs/platform-services.md` | Injected Clock/FileSystem/Clipboard/Terminal backends; deterministic services; POSIX backend usage |
| `docs/api-index.md` | Curated public-header index mapping concepts to headers/classes/examples/tests |

Existing specialized docs (`input-decoder`, `text-width`, `terminal-profiles`,
`golden-format`, `performance`) remain reference material and should be linked
from the new client-facing pages, not used as the primary learning path.

## Source-code policy

Every tutorial/example page must include actual source, not paraphrases only.
For maintainability, code blocks should be generated from checked-in source
where possible:

- Extract full source files for compact examples such as Hello.
- Extract marked snippets for larger examples using stable region markers in
  `examples/<name>/*_app.cpp`.
- Generated snippets must fail the doc build if their source region is missing,
  stale, or empty.
- Snippets must compile as part of the existing examples or dedicated
  doc-snippet compile targets; no uncompiled pseudo-code in public docs.

## Screenshot policy

Every visible widget/example page must include screenshots:

- Hello: initial frame, menu open, info dialog open, dialog dismissed.
- Layouts: full size, narrow resize, hard-too-small state, recovered state.
- Forms: base form, descriptor dialog with invalid field, localized info box,
  wizard page with Next disabled/enabled.
- Workbench: text page, data page, help/command-palette utilities page.
- Graphics: ImageView Sixel, ImageView fallback, Canvas Sixel, Canvas fallback.
- Widget gallery: at least one stable screenshot per widget family; every
  raster-bearing row needs paired Sixel/no-graphics captures.

Screenshots must be generated by tools that drive the real example object graph
through `HeadlessTerminal`/Presenter output. The capture path must never read
widget internals or source images directly.

## Object hierarchy requirement

Every tutorial/example page must show the object tree in a simple text diagram
and explain the ownership boundary. Example:

```text
Application
└── root View
    └── Desktop
        ├── MenuBar (top dock)
        ├── StatusLine (bottom dock)
        └── Window "Hello"
            └── content View / dialog body
```

For each node, the doc must state:

- who owns it;
- how it is inserted;
- how it receives focus/events;
- how it is painted/resized;
- which public header defines it.

## Widget section template

Every widget/component entry in `docs/widget-gallery.md` must follow one
consistent template:

1. **Use when** — practical reason to choose this widget.
2. **Minimal code** — compile-backed snippet.
3. **Object placement** — where it sits in a `Window`, layout, dialog, or
   Desktop dock.
4. **Screenshot** — generated visual state.
5. **Keyboard/mouse behavior** — concise, client-visible grammar.
6. **Callbacks/state** — public methods and callbacks most clients need.
7. **Related examples/tests** — example app and CTest suite.
8. **Common mistakes** — e.g. using manual bounds where layout is better,
   bypassing `CommandPresentation`, reading filesystem directly in widgets.

## Build/tooling work

Add documentation tooling that makes quality enforceable:

- `tools/docgen/extract_snippets.py`: extracts full files or marked regions.
- `tools/docgen/check_docs.py`: verifies every public widget has a doc section,
  at least one snippet, at least one example reference, and screenshot coverage
  where applicable.
- Extend `tools/docgen/generate_docs.sh` to generate new screenshots, extract
  snippets, render HTML/PDF, and fail on missing assets.
- Add CTest gates:
  - `doc_snippet_check`
  - `doc_widget_coverage`
  - `doc_links`
  - `doc_generation_smoke`
- Add a checked-in `docs/coverage.md` matrix:
  public class → guide section → snippet → screenshot → example → test.

## Implementation phases

### Phase 1 — Documentation skeleton and Hello rewrite

- Add `docs/getting-started.md`, `docs/tutorial-hello.md`, and
  `docs/object-model.md`.
- Replace `docs/hello-example.md` or demote it to a verification appendix.
- Include the full Hello source split by file: `hello_app.hpp`,
  `hello_app.cpp`, `main.cpp`.
- Add generated screenshots directly to the Hello tutorial.
- Add an object hierarchy diagram and line-by-line walkthrough.
- Explain command registration, menu/status presentation, modal message box,
  and loop ownership.

Acceptance:

- A reader can copy the documented Hello code and build it.
- Every statement about behavior links to the relevant source line or public
  API.
- The page has at least three generated screenshots.

### Phase 2 — Example-app guides

- Rewrite `docs/example-apps.md` into a real guide, not a verification ledger.
- Add dedicated sections/pages for `gallery`, `filebrowser`, `layouts`,
  `forms`, `workbench`, and `graphics`.
- For each example: purpose, object tree, source snippets, screenshots,
  interaction walkthrough, and “what pattern to reuse in your app”.

Acceptance:

- Every example has at least one object hierarchy diagram, one code snippet,
  one screenshot, and one “client pattern” explanation.
- Existing verification tables move to an appendix or are summarized.

### Phase 3 — Widget gallery

- Create `docs/widget-gallery.md`.
- Cover all public widgets and WP-36B common components:
  `Label`, `StaticText`, `Button`, `InputLine`, `Memo`, `TextView`,
  `CheckGroup`, `RadioGroup`, `ListView`, `TreeView`, `Table`, `ComboBox`,
  `TabControl`, `Progress`, `Scrollbar`, `ScrollViewport`, `Splitter`,
  `ImageView`, `Canvas`, `CalendarView`, `DatePicker`, `TimePicker`,
  `SpinBox`, `Slider`, `SearchBox`, `CommandPalette`, `ToolBar`,
  `BreadcrumbBar`, `PropertyInspector`, `Wizard`, `NotificationCenter`,
  and `Tooltip`.
- Generate screenshots from stable example states or a new doc-only gallery
  capture app that still uses public API.

Acceptance:

- `doc_widget_coverage` proves no public widget header lacks a gallery section.
- No widget row is text-only unless the row explicitly documents why visual
  capture is not meaningful.

### Phase 4 — Layout, dialogs, commands, graphics, platform services

- Add focused conceptual guides:
  - `docs/layout-guide.md`
  - `docs/dialogs-and-commands.md`
  - `docs/themes-and-rendering.md`
  - `docs/graphics.md`
  - `docs/platform-services.md`
- Cross-link these from widget sections and examples.
- Keep advanced terminal/provenance/test material behind “reference” links.

Acceptance:

- A client can answer “which abstraction should I use?” before reading API
  headers.
- Each guide has at least one complete app-level snippet and one screenshot.

### Phase 5 — API index and release-doc gate

- Add `docs/api-index.md` and `docs/coverage.md`.
- Add doc link checking and public-symbol coverage checking.
- Integrate doc checks into CTest.
- Make WP-38 consume `docs/coverage.md` directly for release traceability.

Acceptance:

- Every public header/class has a documented guide location.
- Every documented snippet is generated from or compiled with checked-in code.
- All generated HTML/PDF docs build from a clean tree.

## Non-goals

- Do not turn documentation into a Doxygen dump. A generated class index is
  acceptable, but the primary docs must teach usage.
- Do not document private implementation seams as client API.
- Do not use uncompiled pseudo-code for examples.
- Do not hand-edit generated screenshots or generated HTML/PDF.

## Definition of done

Documentation revamp is complete when:

- `docs/tutorial-hello.md` teaches the full Hello app with code, screenshots,
  object hierarchy, and explanation.
- Every example app has a real guide section with code and screenshots.
- Every public widget/component has a widget-gallery row with snippet,
  screenshot or justified exception, keyboard/mouse grammar, and example/test
  links.
- `docs/coverage.md` has no missing public widget/header rows.
- Documentation generation and coverage checks run in CTest.
- `README.md` points new users to the tutorial path first, not to verification
  and planning documents.
