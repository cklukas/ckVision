# ckVision Text Width and Grapheme Segmentation

`ckv::text` is ckVision's deterministic text-layout policy. It implements
extended grapheme clusters from the Unicode Standard Annex #29 rules and a
fixed terminal-column policy derived from Unicode 15.1.0 character data.
Terminal-specific rendering agreement remains a `term`-layer concern under
the decision log D-019; this module does not read the locale, environment, or
terminal state.

## Pinned Unicode data

The generated header `include/cvision/core/generated_unicode_15_1.hpp` and
the conformance include `tests/generated_unicode_grapheme_break_15_1.inc`
are generated by `tools/unicode/generate_unicode_tables.py`. They are checked
in so every supported platform builds against identical, reviewable data. They
are not edited by hand.

The release is **Unicode 15.1.0**. The generator accepts only these published
Unicode Character Database files:

| File | SHA-256 |
| --- | --- |
| `auxiliary/GraphemeBreakProperty.txt` | `a7e52eee647e52dc210b8719b4d7037276f4b353810293d69377fc46374cec3f` |
| `emoji/emoji-data.txt` | `d7aef489c8fe4c14f09ea5695200277c6b93ac82ac60845cdd2161b0d6835cc1` |
| `EastAsianWidth.txt` | `b08191401dc125f4e84ef262a95754faae6b737c79538e17ea9664a63434e94e` |
| `DerivedCoreProperties.txt` | `f55d0db69123431a7317868725b1fcbf1eab6b265d756d1bd7f0f6d9f9ee108b` |
| `auxiliary/GraphemeBreakTest.txt` | `ed9c5e92fd0911ccbeeb63c97cb19c519ea272ff1112ce843abd991582dd848f` |

The source URLs are rooted at
`https://www.unicode.org/Public/15.1.0/ucd/`. The named files, their hashes,
and the generator are the complete provenance chain for generated data.

To regenerate after intentionally changing the pinned Unicode release, fetch
those five files into a fresh directory (flattened to the filenames in the
table), verify their hashes, then run:

```sh
python3 tools/unicode/generate_unicode_tables.py \
  --input-dir /path/to/unicode-15.1.0 \
  --tables include/cvision/core/generated_unicode_15_1.hpp \
  --grapheme-tests tests/generated_unicode_grapheme_break_15_1.inc
```

Review the generated diff, update this document's version, URLs and hashes,
and run the conformance test and full required gates. Changing the Unicode
release is a normative behavior change and requires a decision log record.

## Grapheme segmentation

`grapheme_end` implements UAX #29 extended-grapheme rules GB3–GB13, GB9c and
GB999 using the complete 15.1 property assignments needed by those rules:
`CR`, `LF`, `Control`, `Extend`, `ZWJ`, `Regional_Indicator`, `Prepend`,
`SpacingMark`, Hangul `L`/`V`/`T`/`LV`/`LVT`,
`Extended_Pictographic`, and the Indic conjunct-break `Consonant`, `Linker`,
and `Extend` properties. `split_graphemes` is its allocation-convenience
wrapper; display and editing code normally iterates with `grapheme_end`.

`tests/test_unicode_grapheme_break.cpp` executes all 1,187 cases from the
pinned official `GraphemeBreakTest.txt`. Project tests additionally exercise
Arabic, Hebrew, South and Southeast Asian marks, rare East-Asian-wide scripts,
emoji/ZWJ/variation selectors, malformed UTF-8, and the library's width
policy.

Malformed UTF-8 is decoded one invalid byte at a time as U+FFFD for purposes
of segmentation and width. This provides deterministic forward progress and
matches `utf8::decode`; callers that are crossing into a rendered Cell use
`sanitize_display_text` to materialize replacement characters.

Callers that must reject malformed data before display processing can use
`utf8::is_valid`. It accepts only well-formed encodings of Unicode scalar
values and distinguishes malformed input from a legitimate encoded U+FFFD
replacement character.

## Column width

`codepoint_width` returns zero for grapheme-control code points (`Control`,
`CR`, `LF`, `Extend`, and `ZWJ`). All other scalar values are two columns only
when their Unicode 15.1 `East_Asian_Width` property is `W` or `F`; they are one
column otherwise. In particular, `A` (East-Asian Ambiguous) is deliberately
one column by default, as specified by D-019.

`grapheme_width` applies the cluster-level policy needed for stable layout:

- a cluster containing VS16 is two columns and one containing VS15 is one;
- a leading regional-indicator pair (a flag) is two columns; and
- an extended-pictographic ZWJ sequence is two columns.

These are ckVision's deterministic layout choices, not an assertion that every
terminal will render every sequence identically. A future terminal capability
may adapt presentation at the `term` boundary without changing this default
library policy.

## Safe clipping and elision

`clip_to_width(text, columns)` returns the greatest complete-grapheme prefix
that fits the supplied terminal-cell budget. `elide_to_width` returns the text
unchanged when it fits, otherwise reserves cells for a complete marker
(U+2026 by default) and appends it after a complete-grapheme prefix. A
non-positive budget returns empty text; a marker too wide for the budget is
itself safely clipped.

These are the only text-truncation operations for widget display. Button,
Window title, Menu, StatusLine, Table and Memo rendering use them or retain
text as explicit grapheme elements. Painter clipping remains the final
geometry guard, but it is not a substitute for deciding truncation in cells.
Inputs, labels, trees, help, static text and text views do not truncate by
byte: they either maintain grapheme-indexed content, wrap by grapheme/cell, or
pass full text to Painter's grapheme-aware cell clip.

## Sanitization

`sanitize_display_text` replaces C0 and C1 controls, `DEL`, and invalid UTF-8
with U+FFFD before application text becomes Cell content. It also replaces
tab and newline: a Cell is single-line, so multi-line widgets split lines
before this boundary. This is the text-to-Cell neutralization required by
the decision log D-040.
